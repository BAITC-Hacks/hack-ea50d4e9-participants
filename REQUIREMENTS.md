# Требования к проекту Career Quest

## 1. Назначение документа

Этот документ переводит исходное техническое задание в набор однозначных и проверяемых требований к MVP. Он описывает, **что** должна делать система, для кого она создаётся, какие данные использует и по каким критериям результат считается готовым.

## 2. Цель продукта

Career Quest — внутреннее веб-приложение, которое помогает сотруднику увидеть путь к следующему карьерному уровню и получить 1–3 персональные рекомендации по развитию. Каждая рекомендация должна быть объяснима: пользователь видит, какие факты повлияли на выбор активности и какой разрыв по навыкам она сокращает.

Для HR система должна показывать агрегированную картину: наиболее частые дефициты навыков, участие в активностях и сотрудников, для которых система не смогла подобрать следующий шаг.

### Целевой результат MVP

Пользователь может пройти сквозной сценарий:

1. Открыть профиль сотрудника.
2. Увидеть текущий и следующий грейд, навыки и историю активностей.
3. Получить 1–3 ранжированные рекомендации с объяснениями.
4. Отметить активность выполненной.
5. Увидеть пересчитанные навыки, прогресс и новые рекомендации.
6. Открыть HR-представление и увидеть обновлённые агрегаты.

## 3. Пользователи и роли

### 3.1. Сотрудник

Основной пользователь со стажем 1–5 лет. Имеет доступ только к собственному профилю, рекомендациям, истории и прогрессу.

Основные потребности:

- понимать требования следующего грейда;
- видеть конкретные дефициты навыков;
- получать реалистичный следующий шаг;
- понимать причину рекомендации;
- видеть эффект завершённой активности.

### 3.2. HR-специалист

Работает с агрегированными показателями и списком сотрудников, требующих внимания.

Основные потребности:

- видеть наиболее распространённые дефициты навыков;
- оценивать участие и завершение активностей;
- находить сотрудников без доступной рекомендации;
- проверять, как система обосновывает рекомендации.

### 3.3. Администратор/демо-оператор

Техническая роль MVP. Загружает набор данных и запускает демонстрационный сценарий. В промышленной версии её функции должны быть отделены от роли HR.

## 4. Термины

| Термин | Определение |
|---|---|
| Навык | Hard- или soft-компетенция с уровнем от 0 до 5. |
| Грейд | Уровень сотрудника внутри карьерного трека, например Middle или Senior. |
| Разрыв навыка | Положительная разница между требуемым уровнем следующего грейда и текущим уровнем сотрудника. |
| Активность | Курс, менторство, проект, выступление или другое развивающее событие. |
| История участия | Факты завершения, пропуска или отказа от активностей за предыдущие 24 месяца. |
| Следующий шаг | Доступная активность, которую рекомендующий модуль предлагает сотруднику. |
| Траектория | Путь от текущего состояния навыков к требованиям следующего грейда. |

## 5. Границы MVP

### Входит в MVP

- импорт `employees.json`, `events.json`, `skills.json`, `activity_history.csv`;
- просмотр профиля и истории сотрудника;
- определение следующего грейда и разрывов по навыкам;
- генерация 1–3 рекомендаций;
- многофакторное ранжирование рекомендаций;
- понятное объяснение каждой рекомендации;
- фиксация завершения активности и детерминированное обновление навыков;
- пересчёт траектории и рекомендаций;
- простой HR-дашборд;
- разделение доступа сотрудника и HR;
- запуск проекта одной командой;
- поддержка загрузки проверочного набора данных той же схемы.

### Не входит в обязательный MVP

- внутренняя валюта и магазин наград;
- публичные рейтинги сотрудников;
- peer-to-peer признание;
- прогноз увольнения;
- интеграции с календарями и мессенджерами;
- промышленная SSO-интеграция;
- полноценный конструктор HR-событий;
- мобильное приложение;
- production-grade мультиязычность.

Эти функции допустимы только после завершения и проверки основного сценария.

## 6. Функциональные требования

### FR-01. Загрузка и проверка данных

Система должна принимать четыре файла стартового набора и дополнительные наборы с той же схемой.

Проверки при импорте:

- обязательные поля присутствуют;
- идентификаторы сотрудников, навыков и событий уникальны;
- ссылки на навыки и события существуют;
- уровень навыка находится в диапазоне 0–5;
- `gain` неотрицателен, `max_level` находится в диапазоне 0–5;
- значения статуса истории входят в поддерживаемый перечень;
- ошибки возвращаются с указанием файла, записи и поля;
- частично некорректный набор не активируется молча.

**Критерий приёмки:** валидный набор импортируется; невалидный набор отклоняется с понятным отчётом, приложение продолжает работать на предыдущем наборе.

### FR-02. Профиль сотрудника

Профиль должен показывать:

- идентификатор сотрудника;
- роль, текущий грейд и стаж;
- следующий грейд, если он определён;
- текущие уровни навыков;
- требования следующего грейда;
- разрывы по навыкам;
- историю завершений, пропусков и отказов;
- доступные следующие шаги;
- общий прогресс к следующему грейду.

**Критерий приёмки:** при открытии произвольного сотрудника все перечисленные данные согласованы с загруженным набором.

### FR-03. Расчёт карьерного прогресса

Прогресс должен рассчитываться детерминированно по навыкам, необходимым для следующего грейда. Рекомендуемая формула для MVP:

```text
progress = sum(min(current_level / required_level, 1) * weight)
           / sum(weight) * 100%
```

Если для роли не найден следующий грейд, система должна показать статус «траектория не определена», а не выдумывать требования.

**Критерий приёмки:** одинаковые входные данные всегда дают одинаковый прогресс; вклад каждого навыка можно показать пользователю.

### FR-04. Формирование кандидатов

Перед AI-ранжированием система должна отфильтровать активности:

- активность применима к роли, грейду или аудитории сотрудника;
- активность развивает хотя бы один релевантный навык;
- активность доступна и ещё не завершена, если повторное прохождение не разрешено;
- эффект активности не превышает её `max_level`;
- активность не предлагается, если она не может изменить ни один релевантный навык.

**Критерий приёмки:** в рекомендации не попадают недоступные или бесполезные активности.

### FR-05. Многофакторная рекомендация

Система должна вернуть от 1 до 3 ранжированных активностей. Выбор должен учитывать минимум три независимых фактора из следующего списка:

- критичность разрыва до следующего грейда;
- величина ожидаемого прироста навыка;
- соответствие роли и грейду;
- история завершений похожих активностей;
- пропуски и отказы от похожих активностей;
- стаж и текущий этап траектории;
- ширина эффекта активности — число закрываемых релевантных разрывов.

Приоритет требований следующего грейда должен быть выше, чем простое правило «выбрать самый низкий навык».

**Критерий приёмки:** на контрольном профиле с низким Public Speaking, повторными пропусками подобных активностей и критичным System Design рекомендация учитывает все эти факты и не выбирает активность только по минимальному уровню навыка.

### FR-06. Объяснение рекомендации

Каждая рекомендация должна содержать:

- название и краткое описание активности;
- затрагиваемые навыки;
- текущий и требуемый уровень ключевого навыка;
- ожидаемый прирост с учётом `gain` и `max_level`;
- факторы истории участия;
- связь с переходом на следующий грейд;
- короткое резюме «почему это следующий шаг»;
- при наличии — предупреждение о неопределённости или компромиссе.

Числа и факты берутся из вычислительного слоя. LLM разрешено использовать для формулировки текста, но не как единственный источник решения.

**Критерий приёмки:** объяснение содержит не менее трёх проверяемых факторов и не противоречит данным профиля.

### FR-07. Завершение активности

При отметке активности выполненной система должна:

1. создать запись в истории;
2. обновить затрагиваемые навыки по правилу `min(current + gain, max_level)`;
3. не допустить уровень выше 5;
4. повторно рассчитать разрывы и прогресс;
5. обновить рекомендации;
6. обеспечить идемпотентность операции — повторный запрос не начисляет прирост второй раз.

**Критерий приёмки:** после завершения активности профиль, траектория и HR-агрегаты показывают согласованное новое состояние.

### FR-08. HR-представление

HR-экран должен показывать:

- частоту дефицитов по навыкам;
- количество и долю сотрудников без рекомендаций;
- участие по активностям: завершения, пропуски, отказы;
- фильтры минимум по роли и грейду;
- переход от агрегата к списку соответствующих сотрудников, если это не нарушает модель доступа.

**Критерий приёмки:** значения дашборда пересчитываются после импорта данных и завершения активности.

### FR-09. Разграничение доступа

- сотрудник видит только свой индивидуальный профиль;
- HR видит HR-дашборд и разрешённые служебные данные;
- API проверяет роль независимо от ограничений интерфейса;
- данные о вовлечённости одного сотрудника не показываются другому сотруднику;
- публичные рейтинги отсутствуют.

Для демо допускается переключатель заранее подготовленных ролей, но архитектура должна позволять заменить его на SSO/RBAC.

### FR-10. Состояния ошибок и отсутствия данных

Интерфейс должен явно обрабатывать:

- сотрудник не найден;
- следующий грейд не определён;
- нет подходящих активностей;
- импорт не прошёл валидацию;
- AI-сервис недоступен или превысил тайм-аут;
- рекомендация не прошла проверку схемы или фактов.

При недоступности LLM система должна вернуть детерминированное ранжирование и шаблонное объяснение.

## 7. Требования к рекомендующему модулю

### 7.1. Предлагаемый подход

MVP использует гибридную схему:

1. Детерминированный слой вычисляет разрывы и допустимые активности.
2. Скоринговый слой ранжирует кандидатов по нескольким факторам.
3. LLM формирует понятное объяснение только на основе переданного контекста.
4. Валидатор сверяет структурированный ответ с исходными фактами.
5. При ошибке LLM используется шаблонное объяснение.

Такой подход сохраняет объяснимость, скорость и воспроизводимость, одновременно демонстрируя уместное применение AI.

### 7.2. Пример прозрачного score

```text
score = 0.35 * grade_gap_criticality
      + 0.25 * expected_skill_gain
      + 0.15 * role_relevance
      + 0.15 * completion_affinity
      + 0.10 * multi_gap_coverage
      - skip_penalty
```

Все компоненты нормализуются в диапазон 0–1. Коэффициенты являются конфигурацией, а не скрытой логикой. Финальные значения следует уточнить на контрольных сценариях.

### 7.3. Формат результата рекомендации

Рекомендующий модуль должен возвращать структурированный результат, например:

```json
{
  "employee_id": "E0028",
  "generated_at": "2026-09-23T10:00:00Z",
  "target_grade": "Senior",
  "recommendations": [
    {
      "event_id": "EV_SYSTEM_DESIGN_01",
      "rank": 1,
      "score": 0.86,
      "facts": [
        {"type": "skill_gap", "skill_id": "SK_SYSTEM_DESIGN", "current": 2, "required": 4},
        {"type": "expected_gain", "value": 1},
        {"type": "history", "completed_similar": 2, "missed_similar": 0}
      ],
      "explanation": "..."
    }
  ],
  "fallback_used": false
}
```

## 8. Нефункциональные требования

### NFR-01. Производительность

- профиль и HR-дашборд: целевое время ответа API до 2 секунд;
- рекомендация с LLM: до 10 секунд;
- при превышении AI-тайм-аута возвращается fallback-результат;
- импорт исходного объёма: 200 сотрудников, 40 событий, 60 навыков и 24 месяца истории без ручной подготовки.

### NFR-02. Воспроизводимость

- проект запускается одной документированной командой;
- конфигурация задаётся через переменные окружения;
- секреты не хранятся в репозитории;
- предусмотрен demo/sample режим без внешнего AI-ключа;
- одинаковая версия данных и конфигурации скоринга даёт одинаковое ранжирование.

### NFR-03. Надёжность и целостность

- запись завершения активности и обновление навыков выполняются атомарно;
- повторная команда завершения безопасна;
- ошибки LLM не повреждают данные;
- смена набора данных не оставляет смешанное состояние старой и новой версии.

### NFR-04. Безопасность и приватность

- принцип минимальных привилегий;
- серверная проверка доступа;
- отсутствие реальных персональных данных в демо;
- журналирование административных действий без записи секретов и полного prompt-контекста;
- защита загрузки от неподдерживаемых типов и чрезмерного размера файлов;
- LLM получает только минимально необходимый обезличенный контекст.

### NFR-05. Наблюдаемость

Минимальные метрики:

- длительность построения рекомендаций;
- доля fallback-ответов;
- число сотрудников без кандидатов;
- ошибки импорта;
- ошибки валидации AI-ответа.

### NFR-06. Удобство использования

- ключевой сценарий доступен без инструкции ведущего;
- причины рекомендации видны рядом с самой рекомендацией;
- прогресс не маскирует конкретные разрывы одним процентом;
- интерфейс не использует манипулятивные механики и публичное сравнение сотрудников.

## 9. Требования к данным

### Основные сущности

- `Employee`: сотрудник, роль, грейд, стаж, текущие навыки;
- `Skill`: навык, категория, требования по ролям/грейдам;
- `Event`: развивающая активность, аудитория, влияние на навыки;
- `ActivityHistory`: участие сотрудника и его результат;
- `RecommendationRun`: версия входных данных, score и факты рекомендации;
- `DatasetVersion`: версия загруженного набора.

### Правила качества данных

- все внешние записи сохраняют исходный идентификатор;
- даты приводятся к единому часовому поясу/UTC;
- неизвестные статусы не интерпретируются автоматически;
- отсутствующее значение отличается от нулевого уровня;
- версия набора прикрепляется к каждому расчёту рекомендации.

## 10. Сквозные сценарии приёмки

### AC-01. Базовая рекомендация

**Дано:** Middle Backend Engineer с разрывом System Design 2 → 4 и подходящей активностью с `gain = 1`.

**Когда:** сотрудник запрашивает следующий шаг.

**Тогда:** активность входит в топ-3, объяснение содержит текущий уровень, требование Senior, ожидаемый прирост и факт истории участия.

### AC-02. Неоднофакторный выбор

**Дано:** Public Speaking — самый низкий навык, но сотрудник трижды пропускал такие активности; System Design критичен для следующего грейда.

**Когда:** строится рекомендация.

**Тогда:** система не выбирает шаг только из-за минимального Public Speaking; приоритет и штраф за историю видны в объяснении/факторах.

### AC-03. Обновление прогресса

**Дано:** рекомендованная активность повышает System Design на 1 до максимума 4.

**Когда:** активность отмечена выполненной.

**Тогда:** уровень изменяется по заданному правилу, прогресс растёт, история пополняется, рекомендации пересчитываются.

### AC-04. Повторное завершение

**Когда:** один и тот же запрос завершения отправлен дважды.

**Тогда:** прирост применяется только один раз.

### AC-05. Проверочный импорт

**Когда:** жюри загружает новый валидный профиль и историю в исходном формате.

**Тогда:** профиль доступен без изменения кода, а рекомендации строятся по новой версии данных.

### AC-06. Отказ AI

**Дано:** LLM недоступна.

**Когда:** запрошена рекомендация.

**Тогда:** пользователь получает ранжированный результат с шаблонным объяснением и признаком fallback, без ошибки всего приложения.

### AC-07. Контроль доступа

**Когда:** сотрудник пытается запросить профиль другого сотрудника или HR endpoint.

**Тогда:** сервер возвращает отказ в доступе и не раскрывает данные.

## 11. Допущения и вопросы для уточнения

До получения стартового набора приняты следующие допущения:

- для каждой роли задан упорядоченный список грейдов;
- требования к следующему грейду доступны в `skills.json`;
- событие содержит аудиторию, `gain` и `max_level`;
- история позволяет отличить завершение, пропуск и отказ;
- у активности есть стабильный идентификатор;
- в MVP прогресс определяется навыками, без оценки вакансий и решений руководителя.

После получения данных необходимо уточнить:

- точные JSON/CSV-схемы и кодировки;
- правила определения следующего грейда;
- допустимость повторного прохождения событий;
- наличие дат доступности и вместимости;
- значение и перечень статусов истории;
- правила для сотрудников на максимальном грейде;
- какие индивидуальные данные разрешено показывать HR в демо.

## 12. Definition of Done для MVP

MVP считается готовым, если:

- все must-have требования реализованы;
- семь сквозных сценариев приёмки проходят;
- новый валидный набор загружается без изменения кода;
- система демонстрирует многофакторный выбор и объяснение;
- отказ LLM не блокирует основной сценарий;
- роли сотрудника и HR разделены на сервере;
- проект запускается по README одной командой;
- подготовлен воспроизводимый демонстрационный сценарий.
