# Career Quest — план архитектуры и реализации

## 1. Цель и границы проекта

Сделать воспроизводимое веб-приложение для кейса **Career Quest**. Сотрудник видит свой профиль, ближайшую карьерную цель, разрывы по навыкам и 1–3 доступных следующих шага с проверяемым объяснением. После отметки активности выполненной приложение пересчитывает модельный прогресс. HR видит агрегированные дефициты компетенций, участие и сотрудников, для которых не нашлось подходящего шага.

Главный критерий качества — рекомендация, учитывающая одновременно целевой грейд, критичность и величину разрыва, ожидаемую пользу активности, историю участия и доступность. Геймификация, награды и прогноз оттока не входят в первый релиз. Кейс Voice Router из общего ТЗ в этот проект не включается: для Career Quest и Voice Router предусмотрены отдельные зачёты.

**Результат хакатона:** работающий основной сценарий, загрузка дополнительных профилей и истории в формате набора данных, объяснимый AI-слой, HR-экран, запуск одной командой, README и демонстрационные сценарии. На этом этапе создаётся только данный план; реализация начнётся после согласования открытых вопросов в разделе 13.

## 3. Пользовательские сценарии и критерии готовности

### Сотрудник

1. Открыть свой профиль: роль, грейд, карьерная цель, оценённые навыки, история и актуальные активности.
2. Увидеть текущий и требуемый уровни каждого важного навыка, прежде всего критичных для ближайшего шага.
3. Получить 1–3 доступные добровольные активности. Для каждой увидеть конкретный ожидаемый прирост, ограничение `max_level`, цель, причины выбора и возможные препятствия.
4. Отметить активность выполненной в демонстрационном режиме. Система один раз применяет её `gain`, пересчитывает разрывы и следующий набор рекомендаций; показывает, что это модельный прогресс до очередной оценки навыков.
5. Если подходящих активностей нет, увидеть честное состояние «пока нет доступного шага» и причину: нет сессии, не выполнены prerequisites, всё подходящее завершено и т. п.

### HR

1. Увидеть долю и количество сотрудников с дефицитом по каждому навыку относительно их выбранного ближайшего целевого профиля, с фильтрами по роли, грейду и подразделению.
2. Найти сотрудников без допустимой рекомендации, не смешивая их с ошибками AI-провайдера.
3. Увидеть участие по активностям: назначения, завершения, пропуски, отказы, просрочки и доли с понятным знаменателем.
4. Не видеть публичный рейтинг «лучших» и «худших» сотрудников.

### Приёмка по ТЗ

| Требование | Проверка |
| --- | --- |
| Профиль и траектория | Открыть произвольного сотрудника, увидеть роль, грейд, историю, навыки и путь к цели. |
| 1–3 рекомендации | Для сотрудника с подходящими кандидатами получить 1–3 разных допустимых шага. |
| Объяснение | В каждой карточке показаны минимум три фактора из набора: цель/грейд, разрыв и критичность навыка, история, пригодность активности и её доступность. Факты сверяются с данными. |
| Обновление | Завершить активность; уровень растёт на `gain` не выше `max_level` и 5; повторное подтверждение не даёт вторую прибавку. |
| HR-view | Доступны дефициты, список без шага и участие по активностям. |
| Проверочные профили | Загрузить новые профили и строки истории без изменения исходных файлов и повторить основной сценарий. |
| Время ответа | Первичный UI/API без AI — до 2 с; рекомендация с AI — до 10 с, включая ограниченный по времени fallback. Измерить на целевой среде. |

## 4. Архитектура

Для масштаба хакатона выбран **модульный монолит**: React + TypeScript для интерфейса, FastAPI + Python для API и расчётов, PostgreSQL для хранения. Один `docker compose up --build` поднимает приложение и БД; инициализация схемы и первичная загрузка набора выполняются идемпотентно. Такой состав отделяет строгую предметную логику от нестабильного внешнего LLM.

```text
Браузер (сотрудник / HR)
        │ HTTPS/HTTP локального демо
        ▼
FastAPI: auth/role guard · import · profile · progress · recommendations · HR
        ├── нормализация и проверка JSON/CSV
        ├── движок навыков и карьерной цели
        ├── фильтры допустимости и числовой ранжировщик
        ├── AI-адаптер: OpenAI / NVIDIA / deterministic fallback
        ├── валидатор объяснения и аудит версии расчёта
        └── PostgreSQL: исходные снимки, импорт, активности, оценки, результаты
```

Разделение внутри backend: `ingestion`, `domain`, `recommendation`, `ai_provider`, `analytics`, `api`. Эти границы нужны для самостоятельного тестирования правил и замены провайдера; микросервисы, очередь задач и векторная БД для данного набора не нужны. Фронтенд получает структурированные причины и числа, а не парсит свободный текст LLM.

### Хранение

Сущности: `dataset_version`, `employees`, `skills`, `role_profiles`, `events`, `activity_records`, `skill_assessments`, `completion_ledger`, `recommendation_runs`, `import_batches`. В `completion_ledger` есть уникальный ключ `(employee_id, event_id, occurrence_id)` для идемпотентного завершения; `occurrence_id` позволяет повторять только `EV_036`. Храним исходный уровень, дату оценки, события-приросты, итоговый модельный уровень, версию каталога и источник изменения. Исходные файлы не редактируются при работе приложения.

При импорте проверяем схему, типы, границы 0–5, уникальность ID, внешние ссылки, роль и грейд, даты, значения статусов, `completion_pct`, `gain`, `max_level`, `prerequisites`. Ошибки показываем по строкам, импорт выполняем целиком или отклоняем целиком. Повторная загрузка одного набора по hash не дублирует записи. Для новых проверочных профилей поддерживаем отдельный batch; связи с общими каталогами разрешаем, конфликт ID обрабатываем явно: `reject` по умолчанию, управляемая замена только в изолированном тестовом batch. Дополнительная история загружается через тот же экран. Проверочный batch можно удалить, не затронув базовый набор.

### Контракты API первого релиза

| Метод и путь | Назначение |
| --- | --- |
| `POST /api/import/preview`, `POST /api/import/commit` | Проверка и загрузка JSON/CSV, отчёт по ошибкам, ID batch. |
| `GET /api/employees`, `GET /api/employees/{id}` | Выбор профиля в демо и подробный профиль с траекторией. |

Структура ответа рекомендаций включает `event_id`, `target_profile`, `skill_impacts`, `eligibility`, `rank_factors`, `reason_evidence`, `explanation`, `provider`, `computed_at`, `dataset_version`. Контракты фиксируются OpenAPI-схемой FastAPI.

## 5. Правило прогресса и траектории

1. **Выбор цели.** Если `career_goal` валиден, показываем его как заявленную долгосрочную цель. Ближайшая веха для текущей роли — следующий грейд (`Junior → Middle → Senior → Lead`). Если цель относится к другой роли, её разрывы считаем отдельно; не обещаем автоматический перевод и не выдаём активность, недоступную сотруднику в его текущей роли/грейде. У `Lead` без иной цели не выдумываем следующий грейд: показываем поддержание навыков и предлагаем задать цель.
2. **Подтверждённый уровень.** `employees.skills` — последняя оценка на `last_review_date`; отсутствующий навык равен 0. История до этой даты уже может быть отражена в оценке, поэтому повторно её не прибавляем.
3. **Модельный уровень.** Прибавляем только завершения после `last_review_date`, дата которых однозначно свидетельствует о завершении после оценки: плановые события с датой сессии после оценки; для `self_paced` — записи с датой зачисления после оценки; плюс новые подтверждения в приложении с точным временем. Если дата записи `self_paced` раньше оценки, фактическое время завершения неизвестно: прирост не добавляем автоматически, помечаем как неопределённый. При каждой прибавке применяем `max(текущий, min(5, max_level, текущий + gain))`: активность не понижает уровень, уже превышающий её потолок. Это расчётная величина, не новая HR-аттестация.
4. **Разрыв.** Для каждого навыка целевого `role_profile`: `gap = max(0, required - modelled_level)`. Отдельно показываем критичные незакрытые навыки. Прогресс по профилю: сумма `min(modelled_level, required)` по требуемым навыкам, делённая на сумму требуемых уровней; итог в процентах. Процент — покрытие требований по навыкам, не вероятность повышения. При смене цели знаменатель и процент меняются.
5. **Завершение в приложении.** Создаём запись в журнале, атомарно пересчитываем прогресс и инвалидируем рекомендации/HR-агрегаты. Нельзя повторно применить ту же завершённую активность, кроме новой отдельной сессии `EV_036`. Если у события нет `develops_skills`, изменение навыков равно нулю.

Важно различать `confirmed` (последняя оценка), `modelled` (по правилам набора данных) и `uncertain` (исторический факт с неоднозначной датой). UI явно показывает эту границу. В перспективе HR может подтвердить новую оценку, после чего она становится базовой и более ранние модельные события перестают учитываться.

## 6. Рекомендательная система

### 6.1. Жёсткий фильтр

Строим кандидатов только из добровольных событий (`mandatory=false`). Проверяем актуальные `target_roles` и `target_grades`, prerequisites по модельному уровню, будущую сессию не раньше `as_of_date` либо постоянную доступность `self_paced`, отсутствие уже завершённой неповторяемой активности и активной записи `in_progress`. Для `EV_036` допускаем повтор, если нет текущей регистрации и соблюдён настраиваемый интервал. Не скрываем причины исключения; HR видит, почему список пуст.

### 6.2. Вычисляемые признаки и baseline

Для каждого кандидата рассчитываем **проверяемые признаки**:

- полезный прирост по навыку после `max_level`, ограниченный незакрытым разрывом до ближайшей цели;
- вес критичных навыков следующего грейда и вклад в долгосрочную цель;
- прогресс в навыках, необходимых как prerequisites для других полезных активностей;
- историю похожих форматов/типов: завершения и оценки повышают уместность, недавние `no_show`/`dropped` снижают, но не запрещают; `declined` по назначению HR/менеджера не превращаем в сильный сигнал предпочтения;
- длительность, формат, рабочий формат сотрудника и дату ближайшей сессии; предпочтение формата — гипотеза, не факт, пока пользователь его не задаст;
- исключение дублей, разнообразие 1–3 шагов и затухание старых сигналов истории.

Базовый рейтинг — прозрачная взвешенная сумма нормированных признаков; стартовые веса задаются в конфигурации и калибруются на проверочных сценариях. Критичный разрыв и достижимый прирост имеют наибольший вес. Веса не называем доказанными результатами обучения: датасет не содержит меток «лучший следующий шаг». Для каждого кандидата сохраняем отдельные факторы, итог и ограничения. Если событие не закрывает текущий разрыв, его можно предложить только как обоснованный подготовительный шаг, а не утверждать, что оно повышает готовность к грейду напрямую.

### 6.3. Роль LLM

Передаём LLM не весь профиль, а обезличенный компактный пакет: целевой профиль, текущие разрывы, критичные навыки, 5–8 лучших допустимых кандидатов, прогнозируемые приросты и агрегированные сигналы истории. Модель **контекстно переупорядочивает** допустимые шаги и выбирает до трёх, учитывая сочетания факторов, которые линейный рейтинг выражает слабо (например, повторные пропуски публичных выступлений при критичном разрыве в системном дизайне). Она возвращает структурированный JSON: ID событий, коды причин из разрешённого словаря, ссылки на ID проверяемых фактов и указание компромисса/неопределённости. Модель не меняет уровни навыков, правила eligibility и числовой прогресс.

После ответа валидатор отклоняет неизвестные/недопустимые ID, несуществующие ссылки на факты, неподтверждённые коды причин и повторы. Числа, факторные пояснения и итоговый текст собирает сервер из проверенных данных и шаблонов; LLM не пишет произвольные фактические утверждения для UI. Таким образом, «AI» влияет на конечный выбор и контекст, а не служит декоративным генератором фразы поверх правила «минимальный навык».

При ошибке API, превышении таймаута, невалидном ответе или отсутствии ключа выдаём 1–3 результата baseline с явной меткой `fallback`. Пустой список кандидатов остаётся пустым, LLM не выдумывает событие. Кэшируем результат по `(employee_id, dataset_version, assessment_version, completion_ledger_version, goal, as_of_date, ranker_version, model_version)`; изменение любого фактора инвалидирует кэш.

### 6.4. OpenAI и NVIDIA

Провайдер выбирается конфигурацией и доступностью ключа. Основной путь для MVP — OpenAI Responses API со строгим JSON Schema для ответа; запасной адаптер — NVIDIA NIM Chat Completions, где структурированный ответ проверяется приложением независимо от возможностей конкретной модели. Точные ID моделей, доступность на ключах, лимиты и цена проверяются отдельным smoke test перед реализацией; имена моделей не зашиваются в бизнес-логику. При провайдерском сбое сначала пробуем другой настроенный провайдер в рамках общего бюджета времени, затем baseline. Не отправляем имена сотрудников, `employee_id`, сырую историю и HR-пометки без необходимости. Ключи — только на сервере, в переменных окружения, без браузера и Git.

Ориентиры по API: [OpenAI Responses](https://developers.openai.com/api/docs/guides/text), [OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs), [OpenAI data controls](https://developers.openai.com/api/docs/guides/your-data), [NVIDIA NIM LLM API](https://docs.api.nvidia.com/nim/re/reference/llm-apis). Использование внешних API для хакатонных синтетических данных допустимо только в пределах правил организатора; для реальных HR-данных потребуется отдельное решение о размещении и передаче.

## 7. Интерфейс

**Экран сотрудника:** компактная карьерная карта «текущий грейд → следующая веха → долгосрочная цель», таблица навыков с подтверждённым/модельным уровнем и требованием, карточки 1–3 рекомендаций с конкретным вкладом и ссылкой на факторы, каталог обязательных активностей отдельно, история и кнопка демонстрационного завершения. Для межролевой цели показываем обе траектории, чтобы не смешивать ближайший грейд и переход в другую роль.

**HR-экран:** фильтры, топ дефицитных навыков по числу и доле сотрудников, распределение статусов участия, список «без подходящего шага» с причиной и переходом к профилю при наличии прав. Нет публичной сравнительной таблицы сотрудников.

**Импорт и демо:** загрузка одного профиля или файла сотрудников и дополняющей истории; предварительный просмотр ошибок; переключатель на проверочный batch; три подготовленных демонстрационных профиля с объяснением, почему простой алгоритм ошибается. Режим выбора произвольного сотрудника доступен только в локальном демо или HR-роли.

Локализация интерфейса: первым языком можно сделать русский, затем казахский и английский. Исходные англоязычные названия навыков и мероприятий сохраняем как канонические значения; переводы храним отдельно и маркируем отсутствующие. Генерация перевода LLM не должна менять ID, уровни и требования.

## 8. Приватность, безопасность и ограничения

- Роли `employee` и `hr`; сотрудник читает только свой профиль и прогресс, HR — данные и агрегаты в рамках разрешённого подразделения. На локальном демо возможен явный переключатель ролей с пометкой «демо»; для реального развёртывания нужен корпоративный SSO. Авторизацию проверяет backend, не только UI.
- История вовлечённости и рекомендации других сотрудников не видны коллегам. Логи API не содержат полных профилей или API-ключей. Импортируем только синтетические записи; произвольные вложения/исполняемый контент не принимаем.
- Содержимое набора и пользовательские тексты считаются данными, а не инструкциями для LLM. Внешнему провайдеру передаём минимальный обезличенный контекст. Потребление токенов и количество вызовов ограничиваем.
- Для конфигурации внешних провайдеров документируем срок хранения, регион и правила обработки данных; без отдельного разрешения не переносим реальный персонал в облачный сценарий.
- Шкала покрытия требований не является оценкой результативности сотрудника и не автоматизирует повышение, увольнение или HR-решение.

## 9. Производительность и отказоустойчивость

Профиль, прогресс и HR-агрегаты считаются локально; целевое p95 для первичного ответа UI/API — до 2 с на наборе и целевой машине. AI-запрос имеет общий дедлайн до 8 с с учётом возможного второго провайдера; до 10 с система обязана показать валидную рекомендацию или понятное состояние. Запросы с одинаковыми входами кэшируются. В UI профиль показывается сразу, рекомендации догружаются отдельно. При недоступности сети сценарии просмотра, завершения и baseline продолжают работать.

Для измерений логируем длительность этапов `load → eligibility → features → provider → validate → response`, выбранный провайдер, число кандидатов и причину fallback без личных данных. Повторная отправка `complete` и импорт после обрыва соединения не создают дублей.

## 10. Проверка качества

1. **Данные и инварианты:** импорт исходного набора и дополнительных профилей, неизвестные skill/event ID, конфликт ID, недопустимые уровни, пустые поля, границы дат, повторная загрузка. Проверка, что исходные 200/40/60/2 743 загрузились без потерь.
2. **Предметные правила:** обязательные активности отсутствуют в рекомендациях; prerequisites и аудитория соблюдены; завершённое событие не повторяется, кроме `EV_036`; `gain` ограничен `max_level`; повторное завершение не увеличивает уровень; отсутствие навыка означает 0; `Lead` без цели не получает фиктивный грейд.
3. **Время и provenance:** дата среза берётся из набора; занятия до/после `last_review_date` обрабатываются без двойного счёта; неоднозначные `self_paced` не превращаются в подтверждённый прогресс. Импорт проверочной истории не меняет базовый batch.
4. **Рекомендация:** минимум три контрастных профиля: (а) низкий некритичный навык против критичного разрыва, (б) история повторных пропусков одного формата, (в) межролевая цель/сложные prerequisites. Сравнить baseline и AI по фиксированной экспертной рубрике: допустимость, вклад в цель, учёт истории, точность объяснения. Не выдавать proxy «будущая запись на курс» за доказанное улучшение карьеры.
5. **Отказы:** недоступные OpenAI и NVIDIA, таймаут, невалидный JSON, галлюцинированный `event_id`, пустой пул кандидатов. Проверить fallback и отсутствие ложных объяснений.
6. **Приёмочные сценарии:** пройти все строки таблицы в разделе 3 через UI; замерить p95 на целевой машине; проверить запуск одной командой с чистого клона и README.

## 12. Риски и решения

| Риск | Решение |
| --- | --- |
| LLM выбирает эффектный, но запрещённый курс | Жёсткий фильтр до LLM, повторная валидация после ответа, fallback. |
| LLM придумывает числа или причинность | Сервер считает и отображает числа; текст ссылается на ID фактов; неподтверждённое объяснение заменяется шаблоном. |
| Исторический `self_paced` ошибочно повышает навык | Прирост только при однозначной дате после оценки; сомнительные случаи выделяются отдельно. |
| Рекомендация усиливает принуждение | Не использовать обязательные процессы, не считать отказ от назначения сильным негативным предпочтением, дать сотруднику выбор. |
| Контрольные профили ломают импорт или правило | Общая схема, изолированные batch, обработка неизвестных ID и контрастные тесты. |
| Ключи/квоты не работают на защите | Детерминированный режим полностью работоспособен; локальный кэш; проверка ключей заранее без публикации секретов. |
| HR-экран раскрывает вовлечённость | Серверная проверка ролей, агрегирование, отсутствие публичных рейтингов. |

## 13. Вопросы владельцу проекта

**Критичные до начала реализации**

1. Сколько часов/дней до дедлайна и сколько человек в команде? От этого зависит объём UI и локализации, а не обязательная логика.
2. Как проходит защита: локально на ноутбуке, в интернете по ссылке или оба варианта? Есть ли Docker на машине показа?
3. Есть ли обязательный стек или уже распределённые технологии в команде? Если нет, предлагается React/TypeScript + FastAPI/Python + PostgreSQL + Docker Compose.
4. Могут ли проверочные профили жюри содержать только новые `employees`/`activity_history` либо также изменённые `skills`/`events`? План импорта поддерживает базовый формат, но этот ответ задаст интерфейс загрузки.
5. Разрешена ли передача обезличенных фрагментов **синтетического** набора во внешние OpenAI/NVIDIA API в рамках правил хакатона? Если нет, AI-слой нужно переключить на локально доступную модель.

**Желательно уточнить**

7. Есть ли лимиты, доступные модели и бюджет у предоставленных OpenAI и NVIDIA ключей? Секреты лучше передать через `.env`, не сообщением и не в репозитории.

10. Есть ли у жюри дополнительные скрытые критерии качества рекомендаций или эталонные ответы на три профиля? Если есть, можно заранее согласовать рубрику оценки.
