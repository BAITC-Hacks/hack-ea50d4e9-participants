# Career Quest: gap-анализ системы по техническому заданию

**Дата аудита:** 23 сентября 2026  
**Основание:** исходное ТЗ HackAlem AI / Halyk Bank и фактическое состояние репозитория.  
**Цель документа:** определить, чего не хватает системе до уверенной защиты и до пилотного внедрения. Это не план переписывания проекта и не требование реализовать все опциональные функции.

## 1. Краткий вывод

Основной must-have сценарий в проекте уже собран: сотрудник видит профиль и траекторию, получает 1–3 многофакторные рекомендации, может смоделировать завершение активности и увидеть пересчёт прогресса; HR видит дефициты, сотрудников без следующего шага и участие; дополнительные профили и история загружаются через интерфейс.

Главный риск проекта сейчас — не отсутствие ещё одного экрана, а недостаток **доказательств качества и устойчивости**. Репозиторий показывает разумную логику, но пока не доказывает, что она стабильно проходит неизвестные проверочные профили, укладывается в лимиты времени, корректно обрабатывает весь контракт данных и защищает права доступа. Для хакатона это важнее магазина наград, валюты или других элементов геймификации.

### Приоритеты

| Приоритет | Что означает | Рекомендуемый фокус |
|---|---|---|

## 3. P0 — чего не хватает до защиты

### P0.1. Формальной матрицы приёмки по каждому must-have

Сейчас есть несколько unit-тестов предметной логики, но нет полного набора проверок «требование → сценарий → ожидаемый результат → автоматический тест». Из-за этого невозможно быстро доказать жюри, что обязательные функции работают не только на одном красивом профиле.

Нужно добавить в процесс проверки:

1. Открытие произвольного сотрудника и согласованность профиля, навыков, истории и следующего грейда.
2. Возврат строго 1–3 рекомендаций при наличии допустимых кандидатов.
3. Наличие в каждой рекомендации минимум трёх **содержательных** факторов, а не только трёх технических меток.
4. Кейсы, где минимальный навык не должен победить критичный разрыв следующего грейда.
5. Кейсы с тремя пропусками похожей активности, отказами, незавершёнными prerequisites, отсутствием будущей сессии, обязательной активностью и уже завершённым неповторяемым событием.
6. Идемпотентность завершения и точное соблюдение `gain`/`max_level`.
7. Пересчёт HR-агрегатов после завершения.
8. Запрет сотруднику видеть чужой профиль и HR API.
9. Валидный и невалидный импорт с понятными ошибками.
10. Работа при недоступности AI-провайдера и возврат детерминированного fallback.

**Критерий готовности:** для всех строк must-have существует автоматический тест и короткий ручной сценарий защиты; результаты тестов приложены к README или артефактам релиза.

### P0.2. Измерения качества рекомендательной системы

ТЗ говорит, что ядро задачи — качество и объяснимость рекомендации. В проекте есть формула ранжирования, но нет набора эталонных кейсов и метрик, показывающих, что она лучше однофакторного правила.

Минимально нужен evaluation-набор из 15–30 синтетических профилей с ожидаемыми свойствами ответа:

- в top-3 присутствует активность, закрывающая критичный gap;
- нерелевантная активность не проходит eligibility;
- частые пропуски снижают позицию, но не уничтожают критически важный путь без альтернативы;
- рекомендация соответствует роли, грейду, prerequisites и расписанию;
- объяснение не содержит фактов, которых нет во входных данных;
- fallback и LLM не расходятся по обязательным ограничениям.

Полезные метрики: `constraint violation rate = 0`, `critical-gap hit@1`, `critical-gap hit@3`, доля рекомендаций с 3+ подтверждёнными факторами, доля профилей без шага, стабильность top-3 при повторном запуске.

**Критерий готовности:** есть воспроизводимый evaluation-отчёт и сравнение хотя бы с baseline «самый низкий навык»; показано, на каких профилях Career Quest принимает более корректное решение.

### P0.3. Полного контракта загрузки проверочного набора

Фактический UI и API загружают только `employees.json` и `activity_history.csv`. `events.json` и `skills.json` не загружаются. Для описанного в ТЗ сценария жюри это может быть достаточно, если проверочные данные используют исходный каталог, однако текущая документация местами обещает импорт четырёх файлов.

Нужно выбрать и явно зафиксировать один контракт:

- **вариант для защиты:** проверочный импорт принимает только новые профили и их историю, а навыки/события обязаны ссылаться на базовый каталог;
- **полный вариант:** batch может содержать все четыре файла и использовать собственную согласованную версию каталога.

Дополнительно не хватает schema/version check, downloadable-шаблона и машинно-читаемого отчёта по ошибкам (`file`, `row`, `field`, `code`, `message`). Сейчас ошибки в основном возвращаются строками и обрезаются первыми 100.

**Критерий готовности:** README, UI и API обещают одинаковый формат; официальный или специально собранный fixture импортируется с чистой БД; неизвестные ID отклоняются до commit; после ошибки активный набор не повреждается.

### P0.4. End-to-end и API-интеграционных тестов

Текущие тесты преимущественно проверяют чистые функции. Не покрыты реальная PostgreSQL-схема, FastAPI endpoints, транзакции импорта, права доступа, кэш, конкурентное завершение и пересчёт HR-view.

Нужны как минимум:

- API smoke suite на временной БД;
- сквозной сценарий: импорт → открыть профиль → получить рекомендации → завершить → увидеть новый прогресс → проверить HR;
- тест атомарности import batch;
- тест удаления batch и связанных записей;
- тест повторной отправки completion;
- тест очистки/инвалидации кэша после изменения данных;
- browser smoke-тест ключевого пути и мобильной ширины.

**Критерий готовности:** чистый `docker compose up --build` поднимает систему, затем одна команда выполняет smoke/e2e без ручной подготовки.

### P0.5. Подтверждённых ограничений по задержке

ТЗ задаёт до 2 секунд для интерфейса и до 10 секунд для AI-рекомендации. В коде есть timeout и поле `duration_ms`, но нет нагрузочных измерений, percentile-метрик и проверки холодного старта.

Нужно измерить отдельно:

- API профиля, прогресса и HR-view на 200 сотрудниках;
- fallback-рекомендацию;
- AI-рекомендацию с каждым включённым провайдером;
- холодный и тёплый запрос;
- импорт максимального разрешённого файла;
- поведение при timeout внешнего AI.

**Критерий готовности:** p95 обычных API < 2 с, полный AI-путь < 10 с, timeout всегда приводит к корректному fallback, UI не остаётся в бесконечном loading-state.

### P0.6. Воспроизводимого release-check

В репозитории есть инструкции и контейнеризация, но в ходе этого аудита запустить проверки не удалось: `python` и `npm` отсутствуют в PATH, а доступ к Docker Engine запрещён. Это не доказывает дефект приложения, но означает, что работоспособность текущего commit не была независимо подтверждена.

Перед защитой нужен зафиксированный release-check:

1. Сборка с нуля без локальных кэшей.
2. Запуск на чистом Docker volume.
3. Проверка health, UI и OpenAPI.
4. Выполнение unit/integration/e2e.
5. Проверка запуска без AI-ключей.
6. Проверка запуска с одним рабочим AI-провайдером.
7. Экспорт логов и скриншотов успешного сценария.

**Критерий готовности:** выбранный commit имеет зелёный CI либо сохранённый протокол локального release-check; у команды есть проверенный офлайн/fallback сценарий демонстрации.

### P0.7. Защиты демонстрационного состояния от случайной порчи

Кнопка «Смоделировать выполнение» делает постоянную запись в БД, а HR может удалять импортированные batch. Для демо это удобно, но последовательные прогоны меняют результаты, и следующая демонстрация может начаться уже с изменённого состояния.

Нужно предусмотреть:

- явную маркировку симуляции;
- reset конкретного demo-профиля или всего demo-state;
- заранее подготовленный неизменяемый профиль для показа;
- подтверждение перед удалением batch;
- snapshot/seed для быстрого восстановления.

**Критерий готовности:** сценарий защиты можно повторить несколько раз с одинаковым начальным результатом не удаляя Docker volume вручную.

## 4. P1 — что существенно усилит продукт и оценку

### P1.1. Объяснение формулы, а не только текстовые причины

Пользователь видит причины и изменения уровней, но не видит, почему активность заняла место №1, насколько на решение повлияли критичность, история, длительность и доступность. Для explainability стоит показывать компактный «паспорт решения»:

- цель/следующий грейд;
- текущий и требуемый уровень;
- ожидаемый прирост с учётом `max_level`;
- влияние истории;
- ограничения и почему кандидат допустим;
- источник решения: fallback или конкретный AI-провайдер;
- дата и версия данных.

При этом нельзя раскрывать сотруднику внутренние данные других людей или создавать иллюзию точной вероятности повышения.

### P1.2. Журнал аудита рекомендаций

Сейчас рекомендации кэшируются в памяти, но нет постоянного audit trail. Для HR и технической защиты полезно хранить обезличенный снимок: версия алгоритма, факторы, список допустимых кандидатов, выбранные event ID, провайдер, latency, fallback reason и timestamp.

Это позволит ответить на вопросы «почему вчера был другой результат», «как часто падает AI» и «не нарушает ли LLM правила». В журнал не следует писать API-ключи, полные prompts с лишними персональными данными или чувствительные поля без необходимости.

### P1.3. Более полезный блок «без следующего шага»

API уже считает причины исключения, но UI списка без рекомендации показывает только сотрудника. HR важно видеть агрегированную причину и действие:

- нет будущих сессий;
- все релевантные активности уже завершены;
- не выполнены prerequisites;
- каталог не покрывает skill gap;
- траектория/следующий грейд не определены.

Стоит добавить группировку причин и переход к профилю с диагностикой. Это превращает дашборд из отчёта в рабочий инструмент улучшения каталога.

### P1.4. Аналитика эффективности, а не только участия

Текущий HR-view показывает количество участий и completion rate. Не хватает связи с развитием:

- какие gaps чаще остаются без покрывающей активности;
- какие программы реально закрывают дефициты по модели;
- в каких ролях/грейдах больше всего непокрытых gaps;
- доля добровольных активностей и отказов;
- динамика по времени;
- coverage каталога: доля gap-навыков, для которых существует хотя бы один допустимый шаг.

Важно не превращать это в публичный рейтинг сотрудников — ТЗ прямо запрещает такую механику.

### P1.5. Корректная локализация

У сотрудников есть `preferred_language`, однако UI не использует это поле для выбора языка. Интерфейс русский, названия и описания событий преимущественно английские, казахской версии нет.

Для качественной локализации нужны:

- RU/KK как минимум для интерфейса, объяснений и ошибок;
- перевод каталога событий и навыков;
- fallback языка при отсутствии перевода;
- единая терминология грейдов и форматов;
- проверка носителем казахского языка;
- тесты, что идентификаторы и бизнес-логика не зависят от перевода.

### P1.6. Улучшение модели истории участия

Сейчас история влияет через завершения похожего типа и пропуски/прерывания того же события. Этого достаточно для MVP, но сигнал довольно грубый. Не хватает различения:

- добровольной и назначенной активности;
- давности события;
- отказа, no-show и прерывания как разных сигналов;
- формата обучения и предпочтений пользователя;
- успешности/оценки, а не только факта завершения;
- причины пропуска, чтобы не наказывать человека за организационные ограничения.

Любое усложнение должно оставаться объяснимым и проверяться на bias. История не должна навсегда закрывать сотруднику критически важное развитие.

### P1.7. Наблюдаемость и эксплуатационные сигналы

Не хватает стандартизированных метрик и диагностических endpoints:

- readiness отдельно от liveness;
- число запросов и ошибок по endpoint;
- latency p50/p95/p99;
- AI success/fallback/timeout rate;
- число кандидатов и доля профилей без шага;
- ошибки импорта по кодам;
- версия приложения/алгоритма в `/health` или `/meta`;
- correlation/request ID и структурированные логи.

### P1.8. UX крайних состояний и доступность

Следует отдельно проверить и доработать:

- профиль максимального грейда без карьерной цели;
- неизвестную/неподдерживаемую карьерную цель;
- пустую историю;
- отсутствие доступных событий;
- длинные переводы и названия;
- ошибки сети и повтор запроса;
- клавиатурную навигацию, focus-state, контраст и screen-reader labels;
- подтверждение необратимых действий;
- маленькие экраны реальных устройств, а не только CSS breakpoint.

## 5. P2 — развитие после обязательной части

### P2.1. Настоящая авторизация и RBAC

Сейчас роль и employee ID приходят из подделываемых HTTP-заголовков, а при `DEMO_MODE=false` защищённые функции просто недоступны. Для пилота нужны SSO/OIDC, серверное сопоставление пользователя с employee ID, роли employee/HR/admin, scope по подразделениям, аудит доступа и политика сессий.

### P2.2. Управление каталогом HR

Конструктор событий должен позволять создавать и версионировать активности, задавать аудиторию, gains, max level, prerequisites, расписание, обязательность и переводы. До публикации нужна проверка, что событие действительно покрывает существующие gaps и не конфликтует со схемой навыков.

### P2.3. Сценарное моделирование

Полезнее простой «вероятности повышения» будет прозрачное what-if моделирование:

- что изменится после выбранных 1–3 активностей;
- сколько критичных gaps останется;
- какая ближайшая достижимая веха;
- альтернативный путь при недоступности события;
- сравнение двух траекторий по времени и нагрузке.

Результат должен называться модельным сценарием, а не обещанием повышения.

### P2.4. Добровольная геймификация

После стабилизации ядра можно добавить персональные вызовы, приватные серии прогресса, peer recognition и внутреннюю валюту. Механики должны быть добровольными, не начислять очки за обязательные процессы и не создавать публичный рейтинг результативности.

### P2.5. Интеграции

Календарь и корпоративный мессенджер имеют ценность для конверсии рекомендации в действие: добавить сессию, напомнить о добровольно выбранном шаге, показать изменение прогресса. Интеграции должны соблюдать согласие пользователя и минимизацию передаваемых данных.

| Риск | Почему это важно | Что проверить/изменить |
|---|---|---|
| Demo headers вместо identity | Любой клиент может объявить себя HR | Использовать только в изолированной защите; для пилота заменить на SSO/RBAC |
| Кэш в памяти процесса | Теряется при рестарте и не согласован между несколькими экземплярами | Для демо допустимо; для масштабирования добавить общий cache или отказаться от него |
| Полная очистка кэша при любом изменении | При росте данных создаёт лишнюю нагрузку | Инвалидировать по employee/batch/version |
| Фиксированный порядок грейдов в коде | Новый грейд или иной карьерный трек потребует изменения кода | Хранить переходы/иерархию в каталоге |
| Специальный repeatable event задан конкретным ID | Логика каталога зашита в код | Сделать repeatability/cooldown свойствами события |
| Completion использует дату набора | Это модельная, а не фактическая дата | Явно показывать режим симуляции; для пилота принимать подтверждённую дату/источник |
| LLM видит до 8 кандидатов | Хороший кандидат ниже top-8 fallback-рейтинга не может быть выбран AI | Подтвердить evaluation; при необходимости применять diversity/coverage selection |
| AI выбирает причины из заранее сформированных кодов | Безопасно, но роль AI ограничена реранкингом | Честно описывать архитектуру: AI не придумывает бизнес-правила, а ранжирует допустимые варианты |
| Нет версионирования алгоритма в результате | Нельзя воспроизвести старую рекомендацию | Добавить `algorithm_version`, dataset version и audit record |
| Импортные ошибки — строки | Сложно подсветить конкретное поле и автоматизировать проверку | Ввести структурированную модель ошибок |
| HR aggregation синхронно обходит сотрудников | На 200 профилях приемлемо, при росте может замедлиться | Замерить p95; затем материализовать/кэшировать агрегаты |
| Нет rate limiting и upload scanning | Риск злоупотребления вне локального демо | Для пилота добавить лимиты, MIME/сигнатуры, антивирусный контур и quotas |

## 7. Рекомендуемая последовательность работ

### Этап A — закрыть доказуемость обязательной части

1. Утвердить точный контракт проверочного импорта.
2. Собрать acceptance matrix из раздела P0.1.
3. Создать эталонный evaluation-набор сложных профилей.
4. Добавить API integration и один browser e2e сценарий.
5. Замерить latency и оформить отчёт.
6. Выполнить чистый release-check и зафиксировать результат.
7. Подготовить reset/snapshot для повторяемой демонстрации.

### Этап B — сделать решение убедительным для жюри

1. Показать сравнение с однофакторным baseline.
2. Добавить паспорт объяснения и версию алгоритма.
3. Раскрыть причины «нет следующего шага» в HR-view.
4. Подготовить три демонстрационных профиля: нормальный, конфликт факторов, отсутствие кандидата.
5. Показать fallback при отключённом AI и стабильность бизнес-ограничений.

### Этап C — подготовить основу пилота

1. SSO/RBAC и аудит доступа.
2. Наблюдаемость, backup/restore и политика хранения данных.
3. RU/KK локализация каталога и объяснений.
4. Версионирование каталога и рекомендательного алгоритма.
5. Интеграции и конструктор событий только после стабилизации ядра.

## 8. Definition of Done для хакатонной версии

Систему можно считать готовой к защите, когда одновременно выполнено следующее:

- все пять must-have требований имеют автоматическую и ручную проверку;
- неизвестный профиль и история загружаются без изменения кода;
- recommendation evaluation показывает преимущество над однофакторным baseline;
- ни один тестовый ответ не нарушает eligibility-ограничения;
- объяснение содержит минимум три подтверждённых входными данными фактора;
- повторное завершение не меняет навык второй раз;
- HR-агрегаты согласованы с профилями и историей;
- employee не получает доступ к чужому профилю или HR endpoint;
- интерфейс отвечает в пределах 2 секунд, AI-путь — в пределах 10 секунд либо корректно уходит в fallback;
- проект поднимается одной командой на чистой машине;
- демо можно повторить с одинакового начального состояния;
- README содержит точный порядок запуска, проверки, импорта и сценарий защиты;
- команда может объяснить, где заканчивается детерминированная бизнес-логика и начинается AI-реранкинг.

## 9. Что не стоит делать до закрытия P0

Не рекомендуется тратить основное время на магазин наград, публичные лидерборды, сложную валюту, прогноз увольнения или большое количество декоративных экранов. Они не закрывают центральный критерий ТЗ — качество и объяснимость следующего шага — и могут ухудшить воспроизводимость основного сценария.

Особенно не следует добавлять публичный рейтинг сотрудников и очки за обязательные процессы: это прямо противоречит ограничениям ТЗ.

## 10. Итоговая оценка готовности

| Область | Оценка | Комментарий |
|---|---|---|
| Функциональный MVP | Высокая | Основной пользовательский путь реализован |
| Качество рекомендации | Средняя | Архитектура разумная, но нет формального evaluation-отчёта |
| Explainability | Средне-высокая | Факторы и evidence есть, не хватает полного паспорта решения и аудита |
| Проверочный импорт | Средняя | Профили/история есть, контракт четырёх файлов не закрыт и не унифицирован в документации |
| HR-view | Средне-высокая | Must-have есть, не хватает диагностики причин и динамики |
| Безопасность | Низкая для пилота, достаточная для локального демо | Demo headers нельзя считать авторизацией |
| Воспроизводимость | Средняя | Контейнеризация и README есть, независимый запуск текущего commit не подтверждён |
| Готовность к защите | Условно высокая | После закрытия P0 проект будет значительно устойчивее и убедительнее |

Главная рекомендация: **не расширять продукт вширь, пока не появятся измеримые доказательства корректности, качества рекомендаций и повторяемости демонстрации**.
